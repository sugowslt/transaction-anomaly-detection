# 이체 판별 입력과 이력 계약

새 이체 모델은 AI Hub 합성 전자금융공동망 데이터의 `이상거래여부` 0/1을 예측합니다. 입력과 이전 거래의 조합에서 학습한 패턴을 찾으며, 경보가 실제 사기나 범죄의 확정을 뜻하지는 않습니다. 모델 점수는 경보 기준과 비교하는 출력값입니다.

## 과거 맥락을 사용하는 API

`POST /api/bank/contextual-events`는 아래 아홉 필드와 `Idempotency-Key` 헤더를 받습니다. 요청 본문에 정답 라벨이나 클라이언트가 만든 과거 이력을 넣을 수 없습니다.

```json
{
  "거래일자": "20241215",
  "출금계좌일련번호": "DEMO-SENDER-01",
  "입금계좌일련번호": "DEMO-RECEIVER-01",
  "출금금융회사일련번호": "DEMO-BANK-01",
  "입금금융회사일련번호": "DEMO-BANK-02",
  "거래금액": 100000,
  "거래시간대": 9,
  "자금구분": "0",
  "매체구분": "2"
}
```

거래일자는 유효한 `YYYYMMDD` 문자열이어야 합니다. 네 식별자는 영문·숫자·`.`·`_`·`~`·`-`로 구성한 1~64자 문자열입니다. 로컬 시연에는 가상 식별자를 사용합니다. 금액·시간대·자금·매체의 허용값은 아래 코드표와 같습니다. 필드가 빠지거나 추가되면 HTTP 400입니다.

서버는 같은 출금계좌의 **거래일자보다 앞선 날짜**에 저장된 거래를 조회합니다. 최근 90일 상세 거래로 7·30·90일 빈도, 금액 습관, 수신계좌 재방문, 채널·자금·시간대 비율을 계산합니다. 90일 이전 기록도 전체 기간의 누적 건수·금액·수신자·상대 금융회사·채널·자금 집계에 반영합니다. 이 집계와 원시 입력을 Python의 공통 특징 함수에 전달하므로 학습과 실시간 판별에 같은 산식을 사용합니다.

데이터에 하루 안의 확정된 거래 순서가 없어 같은 날짜 거래는 서로의 이력에 넣지 않습니다. 같은 출금계좌의 더 늦은 날짜 거래를 이미 판별한 뒤 이전 날짜 요청을 보내면 HTTP 409입니다. 동일 날짜의 별도 거래는 저장할 수 있지만 서로의 과거 맥락으로 사용하지 않습니다.

최근 90일 상세 이력이 20,000건을 넘거나 모델 요청이 4MiB를 넘으면 HTTP 413으로 거부합니다. 이력을 임의로 잘라 정상 응답하지 않습니다. 원본 학습 자료의 최대 상세 이력과 장기 이력은 검증 보고서에 기록합니다.

## 응답과 저장

성공한 새 요청은 HTTP 201입니다. `decision`에 금액·시간대·자금·매체·점수·경보·기준·모델 식별값을 반환하고, `transactionDate`, `historyCount`, `priorSummary`, `observedContext`, `featureSnapshot`에 당시 사용한 날짜와 관측 맥락을 함께 저장합니다. 화면과 조회 응답에는 원시 계좌·금융회사 식별자를 공개하지 않습니다.

- `cold_start`: 이전 날짜의 같은 출금계좌 거래가 없습니다.
- `local_history_unverified`: 로컬에 저장된 이전 거래를 반영했습니다. 계좌의 실제 전체 이력이라고 검증된 상태는 아닙니다.
- `observedContext`: 이전 거래 건수·평균·최대금액·수신자 재방문 등 읽기 쉬운 관측값입니다.
- `featureSnapshot`: 모델에 전달한 로그·비율·코드 변환 후의 특징입니다. 인과적인 경보 설명을 뜻하지 않습니다.

모델 응답의 점수·경보·기준 관계, 이력 범위, 36개 특징 키와 16개 관측값을 검증합니다. 관측값이 서버의 이력과 맞지 않거나 모델 응답이 잘못되면 HTTP 502이며 거래와 판별을 저장하지 않습니다. 모델 연결 실패는 HTTP 503입니다. 거래·맥락·판별 저장은 하나의 DB 트랜잭션으로 처리합니다.

같은 `Idempotency-Key`와 같은 본문을 재시도하면 저장된 응답을 HTTP 200으로 돌려주고 다시 판별·저장하지 않습니다. 같은 키로 다른 본문을 보내거나 구형 API의 키를 재사용하면 HTTP 409입니다. 같은 출금계좌의 이력 조회·모델 요청·저장은 현재 단일 서버 프로세스 안에서 순서대로 처리합니다. 여러 서버 인스턴스를 사용하는 분산 처리 보장은 포함하지 않습니다.

`GET /api/bank/contextual-decisions?limit=20&cursor=...`는 `items`, `nextCursor`, `totalCount`, `totalAlerts`를 반환합니다. `GET /api/bank/contextual-decisions/{id}`로 저장 당시의 상세 근거를 조회합니다. `GET /api/bank/contextual-metrics`는 해당 모델과 해시가 연결된 검증 보고서를 제공합니다.

## 학습 이력과 로컬 이력의 차이

현재 v1 학습은 원본의 날짜순 거래를 사용합니다. **학습 파티션**의 2023년 3분기까지 2,382,445건을 샘플링 없이 모델 학습에 쓰고, 2023년 4분기는 모델·경보 기준 선택에, 2024년 검증 자료는 과거 실험과 비교하는 평가에 사용합니다. 과거 검증 파티션까지 합친 전체 과거 행으로 학습한 결과는 아닙니다. 과거 이력을 구성할 때는 정답 라벨을 사용하지 않습니다. 이미 여러 실험에서 확인한 2024년 자료를 새로운 맹검 시험이라고 주장하지 않습니다.

새 저장소를 실행하면 H2의 과거 거래는 비어 있습니다. 원본 AI Hub 거래를 자동으로 배포하거나 로컬 DB에 넣지 않습니다. 따라서 전체 원본 과거 맥락을 제공한 오프라인 평가와 새 로컬 환경의 첫 판별은 입력 이력 범위가 다릅니다. 이전 네 필드 저장 기록에는 계좌와 거래일자가 없어 새 모델의 이력으로 임의 복원하지 않습니다.

## 구간 종료 후 점검 API

연구 옵션을 켠 서버에서 `POST /api/bank/closed-window-reviews`에 아래 두 값만 전달합니다. 거래·과거 특징·정답을 클라이언트가 함께 보내면 HTTP 400으로 거부합니다.

```json
{"date":"20240502","timeBucket":9}
```

해당 3시간 구간이 끝나지 않았으면 HTTP 409, 저장된 거래가 없으면 404, 연구 경로가 꺼져 있으면 503입니다. 구간 전체 거래를 서버 원장에서 읽고 저장 당시의 66개 과거 특징에 20개 구간 특징을 더해 별도 모델에 요청합니다. 20,000건이나 요청 크기 제한을 초과하면 잘라서 처리하지 않습니다.

새 점검 결과는 HTTP 201로 저장합니다. 응답의 `items`에는 거래별 `decisionId`, 금액, 점수, 경보, 구간 관측값과 검증 범위 제한을 반환합니다. 계좌 식별자는 반환하지 않습니다. 모델 파일·경보 기준의 일치와 점수·경보 관계를 검사하고 관측값 20개를 원장으로 독립 계산해 대조합니다. 실패하면 해당 구간을 완료 처리하지 않습니다.

`GET /api/bank/closed-window-reviews?date=20240502&timeBucket=9`는 저장된 결과를 조회합니다. 같은 구간의 재요청은 같은 결과를 HTTP 200으로 반환하며 새로 추론하지 않습니다. 점검 완료 후 해당 구간에 새 거래를 저장하려 하면 HTTP 409입니다. 기존 거래 요청 키의 재시도는 계속 허용합니다. 구간 점검과 거래 저장은 현재 단일 서버의 공통 잠금으로 동기화합니다.

`GET /api/bank/closed-window-metrics`는 이 모델의 별도 검증 보고서입니다. 이 성능은 거래 직후 판별의 성능과 구분해야 합니다.

일반·동시 거래 전문 모델 조합이 준비되어 있으면 `decisionPolicy`는 `general_or_concurrent_specialist_v1`입니다. `riskScore`는 일반 모델 점수이며 `concurrentScore`는 동시 거래 전문 모델 점수입니다. `generalAlert`, `concurrentAlert`는 각 기준의 결과이고 최종 `alert`는 두 경보의 OR입니다. 일반 점수가 낮아도 전문 모델이 기준을 넘으면 경보가 나올 수 있습니다. 서버는 이 관계와 점수 범위·각 모델 버전·기준값을 검증합니다.

`threshold`는 일반 기준, `specialistThreshold`는 전문 기준입니다. `generalModelVersion`과 `specialistModelVersion`도 저장·재조회 결과에 보존합니다. 두 점수는 각각의 학습 대상에 대한 보정되지 않은 분류기 출력이며, 하나의 실제 사기 확률로 합치지 않습니다. 기존에 저장한 일반 모델 단독 결과는 새 조합으로 다시 계산하지 않습니다.

v1 조회의 `supportAssessment`는 저장된 금액·날짜·이력 상태에 현재 고정된 검증 범위 정책을 적용해 계산합니다. v2와 구간 점검은 당시 판단한 검증 범위도 결과에 저장합니다. 검증 범위 안이라는 표시도 실제 사기 여부나 완전한 이력 수집을 보증하지 않습니다.

## 기존 네 필드 API

`POST /api/bank/events`는 기존 모델 비교와 이전 클라이언트 호환을 위해 거래금액, 거래시간대, 자금구분, 매체구분만 받습니다. 이 경로의 결과는 새 이체 모델의 성능과 구분합니다. 계좌와 금융회사 식별자는 구형 입력과 저장 대상에서 제외합니다.

## 확인 근거

2026년 9월 23일 AI Hub [「이상 판별을 위한 금융거래 정보 및 사용자 패턴 합성데이터」](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=71925) 페이지와 해당 페이지에서 제공하는 구축활용가이드 v1.4를 확인했습니다. 공식 자료는 전자금융공동망의 네 입력 열을 필수값으로 표시하고, 시간대·자금·매체 코드의 범위와 의미를 정의합니다.

| 필드 | 공식 자료 정의 | 이 프로젝트의 입력 |
| --- | --- | --- |
| `거래금액` | 필수, Number | 0 이상 100,000,000,000,000,000 미만, 소수 둘째 자리까지의 JSON 숫자 |
| `거래시간대` | 필수, String | `0`, `3`, `6`, `9`, `12`, `15`, `18`, `21` 중 하나인 JSON 숫자 |
| `자금구분` | 필수, String | 학습 파일에서 확인된 `0`, `1`, `3`, `4` 중 하나인 문자열 |
| `매체구분` | 필수, String | `1`부터 `7`까지 중 하나인 문자열 |

거래시간대 코드는 시작 시각을 뜻합니다. `0`은 00~02시, `3`은 03~05시이며 같은 방식으로 `21`은 21~23시를 나타냅니다.

| 매체구분 | 의미 | 자금구분 | 의미 |
| --- | --- | --- | --- |
| `1` | PC 뱅킹 | `0` | 일반 |
| `2` | 인터넷 뱅킹 | `1` | 급여 |
| `3` | 전화 | `3` | 기타 |
| `4` | 휴대전화 | `4` | 타행 자동이체 |
| `5` | 건별이체 | `11` | 기초생활보장급여(압류금지) |
| `6` | 기타 |  |  |
| `7` | 대량이체 |  |  |

공식 코드표에는 자금구분 `11`이 있지만, 현재 학습 파일과 모델 매핑에서는 확인되지 않았습니다. 학습하지 않은 범주를 임의로 다른 값으로 치환하지 않기 위해 API는 `11`을 HTTP 400으로 거부합니다.

## 요청 예시

```json
{"거래금액":5000000,"거래시간대":9,"자금구분":"0","매체구분":"2"}
```

필드가 빠졌거나 추가 필드가 있거나 자료형과 코드 범위가 다르면 HTTP 400을 반환합니다. 이 계약은 현재 학습 모델이 처리할 수 있는 범위를 나타내며, 공식 코드 전체를 지원한다는 뜻은 아닙니다.

금액은 H2의 `DECIMAL(19,2)` 저장 형식에 맞춰 검사합니다. 소수 셋째 자리 이하에 유효한 값이 있으면 저장 시 반올림될 수 있어, 모델에 전달하기 전에 HTTP 400으로 거부합니다.
상한값에 매우 가까운 금액도 모델의 실수 변환 과정에서 상한값으로 반올림되면 거부합니다.

모델 서비스가 유효한 요청을 거부하거나 경보 여부가 점수와 기준값에 맞지 않으면 HTTP 502를 반환하고 판별 결과를 저장하지 않습니다. 모델 서비스의 오류 본문은 클라이언트에 전달하지 않습니다.

## 중복 요청 처리

`Idempotency-Key`를 붙여 같은 본문을 다시 보내면 저장된 판별을 HTTP 200으로 반환합니다. 같은 키에 다른 본문을 보내면 HTTP 409입니다. 두 요청이 동시에 들어오면 모델 호출은 각각 발생할 수 있지만, 판별은 한 건만 저장되고 나머지 요청에는 저장된 결과를 반환합니다.

## 운영 연동 전에 확인할 사항

공식 자료는 합성 데이터의 열과 코드 정의를 설명하지만, 실제 금융 시스템이 판별 시점에 네 값을 모두 제공한다는 내용은 확인되지 않았습니다. 운영 연동 전에는 거래 승인 흐름의 실제 요청 스키마, 코드 버전, 누락 가능성, 응답 제한 시간을 별도로 확인해야 합니다.
